# Spec Review: hqos-qinq

## Findings

### CRITICAL: Attach/detach/delete are specified as direct control-plane mutations, but the aggregate DRR state lives on a worker thread

The spec says `osvbng_cake_aggregate_attach`, `..._detach`, and `..._delete` directly add/remove children from the aggregate DRR list and update `child->aggregate_index` in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L201) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L214). At the same time, the data-plane design says the aggregate dequeue loop will walk `agg->child_head`, rotate children, and charge parent/child state from the worker thread in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L157) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L181), while the enqueue path continues to rely on the invariant that scheduler state is mutated only by the owner thread in [cake_enqueue.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_enqueue.c#L10).

The current plugin lifecycle path is synchronous from the main/control thread: the API handler calls directly into the scheduler mutation routine in [osvbng_qos_sched_api.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched_api.c#L21) through [osvbng_qos_sched_api.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched_api.c#L45), and that routine directly allocates, frees, and unlinks scheduler state in [osvbng_qos_sched.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L150) through [osvbng_qos_sched.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L306). If aggregate APIs follow the same pattern, detach can unlink the child that the worker is currently servicing, or delete can free aggregate state while the dequeue node still holds a pointer to it. The spec needs an explicit synchronization model: either lifecycle mutations run on the aggregate owner thread via RPC, or they run under a worker barrier after the aggregate is quiesced. Without that, the linked list is not safe.

### HIGH: The new two-phase dequeue structure can starve one class of scheduler, and the aggregate DRR restarts from the wrong place after shaper exhaustion

The spec hard-codes dequeue into Phase 1 for standalone schedulers and Phase 2 for aggregates in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L148) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L195). The existing dequeue node has a single `budget = VLIB_FRAME_SIZE`, iterates active schedulers in bitmap order, and lets each chosen scheduler keep dequeuing until it runs out of packets or shaping budget in [cake_dequeue.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_dequeue.c#L197) through [cake_dequeue.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_dequeue.c#L258). There is no persistent round-robin cursor between node invocations.

That means a busy Phase 1 can consume the whole frame budget before Phase 2 ever runs, so aggregate traffic can sit queued indefinitely behind standalone schedulers. Phase order reversal would create the mirror-image bug. There is a second fairness problem inside Phase 2 itself: each pass starts at `agg->child_head`, and if the aggregate shaper trips at [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L169) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L181), the next invocation restarts from the same head child with the same remaining deficit. With the proposed `65535` quantum in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L66) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L92), one child can hold the head of line for dozens of MTU-sized packets before siblings run. The spec needs one shared arbitration scheme with saved cursors, not two independent full scans that always restart at the front.

### HIGH: Detach-before-drain lets already queued packets escape aggregate shaping and makes `agg->buffer_usage` impossible to keep correct

The spec says detach removes the child from the aggregate list and sets `child->aggregate_index = ~0` before the child scheduler is disabled in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L208) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L214). But Phase 1 skips only children whose `aggregate_index != ~0` in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L150) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L155) and [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L194) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L195). So if the child still has queued packets after detach, those packets stop being parent-shaped and become eligible for standalone dequeue immediately.

The same window breaks the parent buffer counter. The spec charges `agg->buffer_usage` on enqueue and only discharges it on dequeue/drop while `child->aggregate_index != ~0` in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L222) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L240). Once detach clears `aggregate_index`, the already charged bytes no longer have a defined parent to discharge against. The current child teardown path drains queued buffers only later, during scheduler disable, in [osvbng_qos_sched.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L277) through [osvbng_qos_sched.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L280) and [osvbng_qos_sched.h](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.h#L563) through [osvbng_qos_sched.h](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.h#L579), so the `n_children == 0` delete guard in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L214) is not enough. The spec needs a draining state: a child must remain logically attached to its parent until its backlog is zero and all aggregate byte charges are discharged.

### HIGH: The owner-thread pinning model has no load-balancing rule, so a hot S-VLAN can collapse onto one worker and make handoff a permanent bottleneck

The design pins every child in an aggregate to the aggregate owner thread, with ownership chosen by the first packet or inherited from the first child in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L121) through [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/hqos-qinq/IMPLEMENTATION_SPEC.md#L145). The current enqueue path already claims scheduler ownership with a local CAS and hands all wrong-thread packets to `vlib_buffer_enqueue_to_thread()` in [cake_enqueue.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_enqueue.c#L167) through [cake_enqueue.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_enqueue.c#L185) and [cake_handoff.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_handoff.c#L17) through [cake_handoff.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_handoff.c#L50). There is no rebalance path, no least-loaded-thread selection, and no limit on how many aggregates can pin to the same worker.

With hundreds of subscribers under one S-VLAN, that makes one worker responsible for the entire aggregate, while every packet arriving on other workers pays the handoff cost and can hit `CAKE_ERROR_HANDOFF_CONGESTION` in [cake_handoff.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_handoff.c#L47) through [cake_handoff.c](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_handoff.c#L50). Multiple hot aggregates can also land on the same worker because ownership is determined by arrival order, not policy. The spec either needs an explicit admission that one aggregate consumes one worker worth of capacity, or it needs a different placement model that can spread aggregates predictably instead of leaving it to first-packet luck.

## Notes

I did not raise a separate memory-footprint finding for `cake_aggregate_t` itself. One pool element plus one bitmap bit per S-VLAN is small compared with the existing per-subscriber CAKE state, so pool allocation looks appropriate for the aggregate object.

I also did not find a standalone steady-state race on `agg->buffer_usage` from dequeue reinjection alone. On a VPP worker, enqueue/dequeue execution is serialized; the real accounting hazard is the attach/detach/delete transition described above.
