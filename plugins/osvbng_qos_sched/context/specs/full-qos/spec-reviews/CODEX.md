# Spec Review: qos/full-qos

## Findings

### HIGH: The spec has no durable per-session QoS identity, so ad-hoc-rate precedence, policy membership, delete validation, and policy counts cannot be implemented consistently

The design in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L91) and the Phase 1/2 file plan at [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L226), [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L228), and [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L235) assumes the system can answer two questions at runtime: "which active subscribers are using policy X?" and "is this subscriber on the named policy or on an ad-hoc rate that overrode it?" The current codebase does not preserve that information anywhere the conf/show layer can read it. The resolved QoS fields do exist transiently in [`pkg/svcgroup/resolver.go`](/home/brandon/osvbng-dev/osvbng/pkg/svcgroup/resolver.go#L14) and can hold both named policies and ad-hoc rates at once in [`pkg/svcgroup/resolver.go`](/home/brandon/osvbng-dev/osvbng/pkg/svcgroup/resolver.go#L180) and [`pkg/svcgroup/resolver.go`](/home/brandon/osvbng-dev/osvbng/pkg/svcgroup/resolver.go#L230). They also exist in the protocol-local in-memory session state in [`internal/ipoe/component.go`](/home/brandon/osvbng-dev/osvbng/internal/ipoe/component.go#L72). But once a session is published to the subscriber component, only `ServiceGroup.Name` is carried forward in [`internal/ipoe/component.go`](/home/brandon/osvbng-dev/osvbng/internal/ipoe/component.go#L1171) and [`internal/pppoe/session.go`](/home/brandon/osvbng-dev/osvbng/internal/pppoe/session.go#L698). The persisted session models in [`pkg/models/session.go`](/home/brandon/osvbng-dev/osvbng/pkg/models/session.go#L10) have no fields for resolved ingress/egress policy names, rate source, or ad-hoc CIRs, and the subscriber API/cache path only scans those serialized models in [`internal/subscriber/component.go`](/home/brandon/osvbng-dev/osvbng/internal/subscriber/component.go#L84). On top of that, the proposed conf handler would be built with `deps.ConfDeps`, which today exposes neither the subscriber component nor the cache in [`pkg/deps/deps.go`](/home/brandon/osvbng-dev/osvbng/pkg/deps/deps.go#L53).

That gap breaks more than the bulk update path. It also makes `qos.policies` subscriber counts in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L244) and delete validation in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L235) ungrounded. More importantly, the precedence chain at [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L315) is not normalized into a single per-direction "applied QoS source". A subscriber can therefore carry `QoSEgress="residential-100m"` and `DownloadRate=75000` in the resolver result at the same time, use the ad-hoc policer at activation, and later still be matched as a consumer of `residential-100m` during a named-policy bulk update. The spec needs an explicit file-plan change that persists resolved QoS state per session and exposes it to conf/show paths; otherwise the proposed behavior is not implementable from the current session storage model.

### HIGH: Live policy updates race with session activation and release, and the current file plan does not add the serialization needed to keep subscribers converged

The race the spec calls out in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L91) is real under the current control-plane execution model. Session lifecycle handlers are dispatched concurrently by the local event bus in [`pkg/events/local/bus.go`](/home/brandon/osvbng-dev/osvbng/pkg/events/local/bus.go#L96), and `activateSession()` resolves QoS from `cfgMgr.GetRunning()` in [`internal/subscriber/component.go`](/home/brandon/osvbng-dev/osvbng/internal/subscriber/component.go#L375). During a config commit, handlers run before `runningConfig` is swapped to the candidate config in [`pkg/configmgr/conf.go`](/home/brandon/osvbng-dev/osvbng/pkg/configmgr/conf.go#L241) and [`pkg/configmgr/conf.go`](/home/brandon/osvbng-dev/osvbng/pkg/configmgr/conf.go#L296). That means a subscriber activating while `qos-policies.<name>` is being applied still sees the old running config, while the conf handler is trying to push the new policy to the active set it observed earlier. The result is a concrete drift path: the just-activated session can attach the old policer, miss the bulk update, and remain stale after the commit succeeds.

Release is just as exposed. `RemoveQoS()` deletes the southbound bookkeeping entry before it detaches and deletes the policers in [`pkg/southbound/vpp/qos.go`](/home/brandon/osvbng-dev/osvbng/pkg/southbound/vpp/qos.go#L135), so any concurrent updater walking that state can observe a disappearing subscriber and either skip an interface that is still attached in VPP or try to update an index/name that is about to be deleted. `ApplyQoS()` has its own TOCTOU window because it drops the mutex after the existence check and only records the mapping after all VPP API calls finish in [`pkg/southbound/vpp/qos.go`](/home/brandon/osvbng-dev/osvbng/pkg/southbound/vpp/qos.go#L20). The spec currently says "track policy name -> subscriber interface index mapping" in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L236), but that is not enough. It needs a defined serialization strategy across `ApplyQoS`, `UpdateQoS`, and `RemoveQoS`, plus a clear rule for how commits coordinate with session activation so a subscriber cannot straddle old and new policy state.

### HIGH: A mid-bulk `PolicerUpdate` failure leaves partial VPP state, but the spec does not define any transactional or compensating behavior

The apply path in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L93) and [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L285) is "for each subscriber, call `PolicerUpdate`". Under the current config manager, that entire operation is still a single handler invocation for one config path. `Commit()` tracks rollback at the handler-context level in [`pkg/configmgr/conf.go`](/home/brandon/osvbng-dev/osvbng/pkg/configmgr/conf.go#L239), and on failure it only calls each handler's `Rollback()` once per config path in [`pkg/configmgr/conf.go`](/home/brandon/osvbng-dev/osvbng/pkg/configmgr/conf.go#L318). There is no built-in notion of "subscriber 1-37 were already updated in VPP before subscriber 38 failed". If the QoS handler mutates subscribers in-place and then returns an error, the config transaction aborts, `runningConfig` stays old, but some subscribers are already on the new policer parameters.

The spec needs to say how that is recovered. Today even rollback errors are ignored in [`pkg/configmgr/conf.go`](/home/brandon/osvbng-dev/osvbng/pkg/configmgr/conf.go#L325), so "we will rely on config-manager rollback" is not enough. This is especially important because `PolicerUpdate` is by index, not by declarative diff, so the handler has to know the old policer config if it wants to compensate. Without an explicit design for target-set snapshotting, old-value capture, reverse updates on failure, and what happens when compensation itself fails, the live-update feature will create exactly the kind of partial dataplane state the config transaction model is supposed to prevent.

### MEDIUM: The `PolicerAdd` migration solves the wrong problem and adds mixed-mode lifecycle risk the spec does not account for

The Phase 1 file plan says to switch `ApplyQoS()` from `PolicerAddDel` to `PolicerAdd` because the latter returns an index in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-context/components/qos/full-qos/IMPLEMENTATION_SPEC.md#L226). But `PolicerAddDelReply` already returns `PolicerIndex` today in [`pkg/vpp/binapi/policer/policer.ba.go`](/home/brandon/osvbng-dev/osvbng/pkg/vpp/binapi/policer/policer.ba.go#L217), just like `PolicerAddReply` in [`pkg/vpp/binapi/policer/policer.ba.go`](/home/brandon/osvbng-dev/osvbng/pkg/vpp/binapi/policer/policer.ba.go#L254). The actual compatibility problem called out in the current southbound code is not policer creation; it is the broken V2 attach APIs in VPP v25.10, documented in [`pkg/southbound/vpp/qos.go`](/home/brandon/osvbng-dev/osvbng/pkg/southbound/vpp/qos.go#L3), which lines up with the generated `PolicerInputV2` and `PolicerOutputV2` interfaces in [`pkg/vpp/binapi/policer/policer.ba.go`](/home/brandon/osvbng-dev/osvbng/pkg/vpp/binapi/policer/policer.ba.go#L811) and [`pkg/vpp/binapi/policer/policer.ba.go`](/home/brandon/osvbng-dev/osvbng/pkg/vpp/binapi/policer/policer.ba.go#L964).

That matters because the spec's migration leaves the implementation in a mixed mode anyway: index-based create/update/delete via `PolicerAdd`/`PolicerDel`/`PolicerUpdate`, but name-based attach/detach via `PolicerInput`/`PolicerOutput` and name-based dump via `PolicerDump` if the V2 attach path remains broken. The current naming scheme is already needed for attach/detach, so switching the creation API buys little while adding another lifecycle state to keep consistent. The simpler path is to keep `PolicerAddDel`, start recording the returned `PolicerIndex`, and defer any creation/deletion API migration until the V2 attach bug is actually gone. As written, the spec introduces migration scope and recovery edge cases without solving the real blocker.
