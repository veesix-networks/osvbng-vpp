# Spec Review: cake-scheduler

## Findings

### CRITICAL: Resuming dequeue directly at `interface-output-arc-end` skips the rest of the output feature arc

The spec says queued packets are dequeued to `interface-output-arc-end` to "resume the normal output feature arc" in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L104) and [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L467). That is not how VPP feature arcs resume. The canonical pattern is that a feature node which wants the packet to continue calls `vnet_feature_next()`, which consumes `b->current_config_index` and returns the next enabled feature on that arc, as documented in [`registration.c`](/home/brandon/osvbng-dev/vpp/src/vnet/feature/registration.c#L55) and implemented in [`feature.h`](/home/brandon/osvbng-dev/vpp/src/vnet/feature/feature.h#L303). The `interface-output` arc explicitly has other nodes before the arc end, including `span-output` and `ipsec-if-output`, in [`interface_output.c`](/home/brandon/osvbng-dev/vpp/src/vnet/interface_output.c#L1369).

That makes the proposed resume point incorrect. By the time `cake-enqueue` executes, `current_config_index` already points at the next feature after CAKE, not at the arc start, so hard-jumping to `interface-output-arc-end` bypasses every later output feature on that interface. The current scaffold mirrors the same mistake by hard-coding `interface-output-arc-end` as the dequeue next node in [`cake_dequeue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_dequeue.c#L118) and [`cake_dequeue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_dequeue.c#L324). The spec needs a different resume design: either dequeue by calling `vnet_feature_next()` on the stored buffer state, or re-enter the `interface-output` arc with an explicit "already queued by CAKE" marker so CAKE does not loop on itself.

### CRITICAL: The enqueue/dequeue design does not define a safe buffer-ownership transition for queued packets

The design stores live VPP buffer indices in per-flow queues between [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L104) and [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L397), but never states exactly when the scheduler becomes the sole owner of the buffer, and exactly which paths must free it. That omission matters because VPP buffer lifetime is explicit: buffers carry a `ref_count` in [`buffer.h`](/home/brandon/osvbng-dev/vpp/src/vlib/buffer.h#L98), and `vlib_buffer_free_one()` frees the whole chain once that count reaches zero in [`buffer_funcs.h`](/home/brandon/osvbng-dev/vpp/src/vlib/buffer_funcs.h#L946) and [`buffer_funcs.h`](/home/brandon/osvbng-dev/vpp/src/vlib/buffer_funcs.h#L1015).

The current scaffold shows the concrete failure mode the spec is leaving open. `cake_enqueue` pushes `bi0` into the flow queue, then sends the same buffer to `error-drop` in [`cake_enqueue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_enqueue.c#L198) and [`cake_enqueue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_enqueue.c#L225). No refcount is incremented first. That means the queued index can already be freed before `cake_dequeue` later touches it. The disable path has the opposite problem: it frees the queue vectors but leaves the queued buffers themselves unfreed in [`osvbng_qos_sched.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L258). The spec needs an explicit invariant such as: "enqueue consumes the packet without forwarding it anywhere; queued buffers remain owned by the scheduler until exactly one of dequeue transmit, AQM/overflow drop, subscriber teardown, interface delete, or handoff-congestion drop frees them." Without that invariant, this design will oscillate between use-after-free and leaks.

### CRITICAL: Preserving `current_config_index` in the buffer is not sufficient across live feature reconfiguration

The spec assumes that preserving `current_config_index` across queueing is enough to resume later in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L470). In VPP, `current_config_index` is only an index into the feature config heap, stored directly in the buffer in [`buffer.h`](/home/brandon/osvbng-dev/vpp/src/vlib/buffer.h#L111). `vnet_get_config_data()` dereferences that heap entry immediately in [`config.h`](/home/brandon/osvbng-dev/vpp/src/vnet/config.h#L90). Old feature configurations are reference-counted per configured user and are freed as soon as the last reference goes away in [`config.c`](/home/brandon/osvbng-dev/vpp/src/vnet/config.c#L190).

Queued packets do not hold a reference to the old feature config. So if the `interface-output` feature set changes while CAKE is holding packets, the stored `current_config_index` can point into freed config-heap state by the time dequeue tries to resume. This is not theoretical for this spec: Phase 7 explicitly wants live policy changes in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L807), and subscriber release is part of the normal lifecycle in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L806). The spec needs to define one of three safe behaviors: drain all queued packets before any output-feature reconfiguration on that interface, pin the old config until the scheduler drains, or re-inject at a stable entry point and recompute the output feature path instead of resuming from a stale config cursor.

### HIGH: The "one scheduler owner thread per interface" model does not match VPP's TX queue model

The threading model in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L474) assumes an interface has a single owning worker thread, and that the normal output path already runs there. VPP's TXQ infrastructure is more flexible than that. The output node builds per-thread runtime data for every interface in [`tx_queue.rst`](/home/brandon/osvbng-dev/vpp/src/vnet/interface/tx_queue.rst#L22) and [`runtime.c`](/home/brandon/osvbng-dev/vpp/src/vnet/interface/runtime.c#L187). TX queues can be placed on main or any worker threads via `sw_interface_set_tx_placement` in [`tx_queue.rst`](/home/brandon/osvbng-dev/vpp/src/vnet/interface/tx_queue.rst#L115), a thread can have multiple TX queues for the same interface in [`tx_queue.rst`](/home/brandon/osvbng-dev/vpp/src/vnet/interface/tx_queue.rst#L43), and queues can be shared across multiple threads in [`tx_queue.rst`](/home/brandon/osvbng-dev/vpp/src/vnet/interface/tx_queue.rst#L68).

That directly conflicts with the plugin's current `sw_if_index -> (thread_index, pool_index)` mapping in [`osvbng_qos_sched.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L220). Wrong-thread packets are already treated as a special case in [`cake_enqueue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_enqueue.c#L91), but under multi-TXQ placement or later queue-placement changes, that path stops being a safety net and becomes a normal-data-path requirement. The spec needs to choose a model that actually matches VPP: per-thread scheduler state keyed by `(sw_if_index, thread_index)`, or per-TXQ scheduler state keyed by queue placement, plus an explicit rebalance path when TX queue placement changes under the interface.

### HIGH: The memory model is too large for "thousands of subscribers", and `buffer_limit` does not bound real buffer-pool pressure

The design fixes `CAKE_QUEUES=1024` flows per tin and up to 8 tins per subscriber in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L154), with each `cake_tin_t` embedding `flows[1024]` in [`osvbng_qos_sched.h`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.h#L114). By field layout in [`osvbng_qos_sched.h`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.h#L79), a 64-bit build makes each `cake_flow_t` roughly 80 bytes before any queued-packet vector storage. That is roughly 80 KiB of flow state per tin, roughly 320 KiB static per subscriber for the default 4-tin mode, and roughly 640 KiB static per subscriber for 8 tins. At 10,000 subscribers, that is already on the order of 3.2 to 6.4 GiB of resident scheduler state before a single packet is queued.

The queued-packet budget is also under-specified. Auto `buffer_limit` is `rate * interval * 1.5` in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L595) and [`osvbng_qos_sched.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.c#L209). At 100 Mbps, that is about 1.875 MB per subscriber; at 10,000 subscribers, it is about 18.75 GB of queued payload. More importantly, VPP buffer exhaustion is not a byte-only problem: small packets pin whole buffer objects, and chained packets pin multiple buffer objects, regardless of payload length. So the spec's byte-only `buffer_limit` does not bound actual buffer-pool depletion. The design needs lazy allocation of tins/flows, lower default table sizes, and a second admission control based on packet/segment counts or free-buffer watermarks, not just queued bytes.

### MEDIUM: The idle `INPUT` node is not "effectively zero cost" unless the spec disables it when unused

The spec claims that, when idle, the dequeue node costs only "one bitmap check per iteration" in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L112). In VPP, every `VLIB_NODE_STATE_POLLING` input node is dispatched on every main-loop iteration in [`main.c`](/home/brandon/osvbng-dev/vpp/src/vlib/main.c#L1548). The current scaffold registers `cake-dequeue` as permanently polling in [`cake_dequeue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_dequeue.c#L324), so even the early return on an empty bitmap in [`cake_dequeue.c`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/cake_dequeue.c#L111) still pays a node dispatch on every worker.

This is not a correctness bug, but the spec should not describe it as free. VPP supports disabling input nodes entirely in [`main.c`](/home/brandon/osvbng-dev/vpp/src/vlib/main.c#L853), so the design should explicitly require `vlib_node_set_state(..., VLIB_NODE_STATE_DISABLED)` when there are no active schedulers on any thread, and only switch to polling when the first scheduler becomes active.

### MEDIUM: IPv6 5-tuple extraction breaks on extension headers and fragments

The flow-hash design assumes TCP/UDP ports directly follow the fixed 40-byte IPv6 header in [IMPLEMENTATION_SPEC.md](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/context/specs/cake-scheduler/IMPLEMENTATION_SPEC.md#L238). The current helper in [`osvbng_qos_sched.h`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.h#L277) does exactly that and already carries a TODO for hop-by-hop, routing, and fragment headers in [`osvbng_qos_sched.h`](/home/brandon/osvbng-dev/osvbng-vpp-plugin-qos/src/osvbng_qos_sched.h#L292).

That means fragmented IPv6 packets and any packet with extension headers will either hash on the wrong bytes or fail to find the L4 ports at all, collapsing unrelated traffic into the same flow bucket. The spec needs an explicit IPv6 extension-header walk and a policy for fragments without an immediately available L4 header, otherwise per-flow fairness is wrong for a non-trivial subset of IPv6 traffic.
